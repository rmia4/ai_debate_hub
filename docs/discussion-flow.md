# 토론 진행과 MCP 도구

토론방을 만들 때 **동시 방식**과 **순차 방식** 중 하나를 고릅니다. 서버는 도구 4개로 기록 저장, 차례 관리, 합의 판정을 처리합니다.

## 진행 흐름

### 동시 방식 (`parallel`)

매 라운드 양쪽이 각자 한 번씩 답변합니다.

1. 사용자가 웹에서 토론방을 만듭니다(주제, 배경 설명, 진행 방식, 최대·최소 라운드). 서버가 토론 ID와 참여자별 지시문을 발급합니다.
2. 지시문을 복사 버튼으로 각 채팅에 붙여 넣습니다.
3. 라운드 1: 각 AI가 상대 답변을 보지 않은 채 독립 답변을 `submit`합니다.
4. 사용자가 양쪽에 "다음 라운드 진행"을 입력합니다.
5. 각 AI가 `get_state`로 직전 라운드의 양쪽 답변과 합의 후보를 읽고, 검토·반박·수정안과 합의 상태를 `submit`합니다.
6. 양쪽이 같은 라운드에서 같은 합의안 ID에 동의하고 남은 이견이 없으면 "합의 완료"로 표시합니다. 다음 `get_state`에서 AI가 종료를 알립니다.
7. 최대 라운드에 도달하면 "최대 라운드 도달·합의 미확정"으로 종료합니다.
8. 사용자는 웹에서 라운드별 기록, 쟁점, 결론을 확인합니다.

### 순차 방식 (`sequential`)

두 AI가 한 턴씩 번갈아 답변하고, 사인이 연속되면 종료합니다.

1. 웹에서 진행 방식 "순차"를 골라 토론방을 만듭니다. 선공은 지정하지 않습니다.
2. 지시문을 양쪽 채팅에 붙여 넣습니다.
3. 사용자가 먼저 지시한 AI가 첫 의견을 `submit`하면 그 AI가 선공이 됩니다. 어느 쪽에 먼저 지시해도 됩니다.
4. 이후에는 차례인 쪽에만 "다음 진행"을 입력합니다. 차례가 아닌 AI가 제출하면 서버가 "상대 차례입니다"를 반환합니다.
5. 각 턴은 이의 제기, 수정안(`proposal`) 제시, 사인 중 하나입니다. 사인은 "현재 합의안을 수정 없이 받아들인다"는 뜻입니다.
6. 수정안이 나오면 그때까지의 사인은 초기화됩니다. 수정안을 낸 쪽은 같은 턴에 사인할 수 없습니다.
7. 사인이 연속 두 번 나오면 합의 완료로 종료합니다.
   - A 수정안 → B 사인 → A 사인 = 종료
   - A 수정안 → B 사인 → A 재수정안 = 사인 초기화 후 계속
8. 최대 턴(기본 10)에 도달하면 "최대 턴 도달·합의 미확정"으로 종료합니다.

## MCP 도구 명세

도구는 4개로 제한합니다. 서버는 OAuth 액세스 토큰으로 **사용자**를 판별하고(판별은 "요청 → 사용자" 함수 한 곳에서만 합니다), 토론의 자리는 `get_state`·`submit`의 `seat`(`A`/`B`) 입력으로 받습니다. 같은 AI의 두 채팅은 같은 연결(토큰)을 쓰므로 토큰으로는 자리를 구별할 수 없기 때문입니다. 자리는 지시문에 적혀 있고, AI는 토론 내내 같은 값을 넣습니다. 모든 도구는 토큰 소유자의 토론방만 조회·수정합니다.

- 자리를 잘못 넣는 것은 본인 토론방에서 본인 AI가 하는 실수이므로 보안 경계가 아닙니다. 차례 검증(`not_your_turn`)과 "이미 제출됨" 응답이 대부분의 혼동을 막습니다.
- 각 답변에는 제출한 연결의 앱 이름(`client_name`)을 함께 남겨 웹 기록에 "A석 · Claude"처럼 보여 줍니다.

| 도구 | 입력 | 반환 | 비고 |
| --- | --- | --- | --- |
| `start_discussion` | `topic`, `context`(선택), `mode`(`parallel`/`sequential`, 기본 `parallel`), `max_rounds`(동시 기본 5, 순차 기본 10), `min_rounds`(동시 기본 2) | `discussion_id`, 자리별(`A`/`B`) 지시문 | 웹 생성이 기본이고, 채팅에서 만들 때만 사용. 접속 주소·비밀값은 반환하지 않음. 동시: 2 ≤ `min_rounds` ≤ `max_rounds` ≤ 10, 순차: 4 ≤ `max_rounds` ≤ 20 |
| `get_state` | `discussion_id`, `seat` | 주제·배경, 진행 방식, 현재 라운드(순차는 턴), 내 차례·제출 여부, 직전 답변(동시: 양쪽, 순차: 상대 직전 턴), 각 답변의 동의 대상 ID, 합의 후보 목록(완료된 라운드의 `proposal` ID·라운드·제안자·본문), 순차 방식의 현재 합의안과 사인 현황, 토론 상태 | 동시 방식 라운드 1은 상대 답변 없음. 진행 중인 라운드의 새 합의안은 상대에게 숨김. 순차 방식에서 아무도 시작하지 않았으면 "먼저 제출하면 선공"을 안내 |
| `submit` | `discussion_id`, `seat`, `expected_round`, `content`, `proposal`(선택), `open_issues`, 동시 방식: `agreement`·`accepted_proposal_id`, 순차 방식: `sign` | 접수 결과, 다음 차례, 합의 판정 결과 | 같은 번호의 기존 제출이 있으면 그 결과 반환(재시도). 순차 방식은 `agreement`를 받지 않음 |
| `get_summary` | `discussion_id` | 진행 중: 완료된 라운드·턴만 / 종료 후: 전체 기록과 결론. 각 답변의 합의안 ID와 본문 포함 | 진행 중인 라운드 답변은 노출하지 않음 |

### 필드 의미

- `proposal`: 이 답변이 제시하는 최종안 본문입니다. 함께 제출되면 그 답변 ID가 곧 합의안 ID입니다. 순차 방식에서는 가장 최근 `proposal`이 현재 합의안입니다.
- `agreement`(동시 방식만): `agree`(동의) / `partial`(부분 동의) / `disagree`(반대). 순차 방식은 `sign`과 겹치므로 받지 않고, 웹 표시용으로 서버가 파생합니다(사인 = 동의).
- `accepted_proposal_id`(동시 방식): 같은 토론의 완료된 라운드 답변 중 `proposal`이 있는 것(자신 또는 상대)만 지정할 수 있습니다.
- `sign`(순차 방식): 현재 합의안을 수정 없이 받아들일 때 `true`.
- `open_issues`: 아직 남은 이견을 짧은 문장 배열로 냅니다.
- 재시도 판별은 `expected_round`와 `(토론, 라운드, 참여자)` 유니크 제약으로 합니다. 별도 `request_id`는 두지 않습니다. 같은 번호로 다른 내용을 보내면 "이미 제출됨, 수정되지 않음" 오류와 함께 저장된 제출을 반환합니다.
- 도구 설명(description)에 "쉽게 동의하지 말고 근거를 제시할 것"을 명시합니다.

### 허용되는 제출 조합

동의와 수정안은 한 제출에서 함께 낼 수 없습니다. 서버는 다음 조합만 받습니다.

| 방식 | 제출 종류 | 필수 규칙 |
| --- | --- | --- |
| 동시 | `agree` | `accepted_proposal_id` 필수, 새 `proposal` 금지, `open_issues` 빈 배열 |
| 동시 | `partial` / `disagree` | `accepted_proposal_id` 사용 안 함, `proposal`은 선택 |
| 순차 | 사인 (`sign=true`) | 새 `proposal` 금지, 현재 합의안 존재, `open_issues` 빈 배열 |
| 순차 | 이의·수정 (`sign=false`) | `proposal`은 선택 |

### 공개 규칙

웹은 사용자에게 진행 중인 라운드의 제출도 보여 줍니다. 하지만 AI가 쓰는 MCP 조회 경로(`get_state`, `get_summary`)에는 "완료된 라운드만 공개" 규칙을 적용합니다. 그래야 동시 방식에서 상대 답변을 미리 볼 수 없습니다.

## 합의 판정 규칙

`submit` 처리 시 트랜잭션 안에서 수행합니다.

### 공통 처리 순서

재시도가 검증에 막히지 않도록 기존 기록 조회를 검증보다 먼저 합니다 ([PostgreSQL 명시적 잠금](https://www.postgresql.org/docs/current/explicit-locking.html)).

1. 해당 `discussions` 행을 `SELECT … FOR UPDATE`로 잠급니다. 웹의 강제 종료·설정 변경도 같은 잠금을 거칩니다.
2. 이 참여자의 `expected_round` 제출 기록을 조회합니다.
3. 기록이 있으면 새로 저장하지 않고 저장된 제출과 현재 토론 상태를 반환합니다. 내용이 다르면 "이미 제출됨, 수정되지 않음"을 함께 알립니다.
4. 기록이 없을 때만 종료 여부(`active`가 아니면 거부), 라운드·턴 번호, 차례, 제출 조합 규칙을 검증합니다.
5. 새 제출을 저장하고 아래 방식별 규칙으로 상태를 갱신합니다.
6. 상태 갱신 순서는 **합의 판정 → (합의가 아닐 때만) 최대 횟수 판정 → (계속할 때만) 번호 증가**입니다. 그래야 마지막 턴의 합의가 `max_reached`로 덮이지 않고, 종료 후 `current_round`가 최대값을 넘지 않습니다.

웹에서 강제 종료하면 `closed`로 바뀌며, 이후 새 제출은 거부합니다.

### 동시 방식

1. `expected_round`가 `current_round`와 다르면 거부하고 `get_state`를 다시 호출하라고 안내합니다.
2. `agree`이면 `accepted_proposal_id`가 같은 토론의 완료된 라운드 답변이고 `proposal`을 가졌는지 검증합니다.
3. 답변을 저장합니다. 상대가 이번 라운드에 아직 제출하지 않았으면 여기서 끝납니다.
4. 상대도 제출했다면 라운드를 마감합니다. 양쪽 모두 `agree`이고, `accepted_proposal_id`가 같고, 현재 라운드 ≥ `min_rounds`이면 `agreed`로 종료하고 `agreed_proposal_id`를 기록합니다.
5. 합의가 아니고 현재 라운드가 `max_rounds`이면 `max_reached`로 종료합니다.
6. 둘 다 아니면 `current_round`를 1 올립니다.

### 순차 방식

1. 아직 제출이 없으면 이번 제출자를 `starter`로 기록하고 턴 1로 저장합니다. 두 요청이 동시에 와도 잠금 때문에 먼저 처리된 쪽만 선공이 됩니다. 나중 요청은 "상대가 먼저 시작함"으로 거부되어 `get_state`부터 다시 진행합니다.
2. 직전 턴 제출자와 같은 참여자면 "상대 차례"로 거부합니다.
3. `expected_round`가 현재 턴과 다르면 거부합니다.
4. 답변을 저장합니다.
5. 직전 턴과 이번 턴이 모두 `sign=true`이면(사이에 새 `proposal` 없음) `agreed`로 종료하고 현재 합의안을 `agreed_proposal_id`로 기록합니다. 수정안 제안자는 상대 사인 뒤에 직접 사인해야 확정됩니다.
6. 합의가 아니고 현재 턴이 `max_rounds`이면 `max_reached`로 종료합니다.
7. 둘 다 아니면 턴을 1 올립니다.

## 쟁점 추적

`open_issues`는 자유 문장이라 라운드 간 같은 쟁점을 자동으로 묶기 어렵습니다. 1단계는 라운드별 목록만 보여 줍니다. 필요하면 `submit`에 `resolved_issues`를 추가해 해소/미해소를 구분합니다.
